# 视频无损分割 · NAS 版

把超大视频切成多段，**全程不重新编码**，画质音质零损失。给 NAS 用：加几个监控文件夹，
新拷进来的视频自动发现并处理；也可以设定时任务在空闲时段批量跑。所有参数都在网页上改。

支持两种部署形态：**Docker** 和 **飞牛 fnOS 应用（fpk）**。

---

## 它解决什么问题

相机、运动相机、无人机拍出来的单个文件动辄 10~60GB，拷进 NAS 之后：

- 手机、电视、剪辑软件打不开这么大的文件；
- 想传给别人，单个文件太大传不动；
- 有些平台对单文件大小有限制。

这个工具按大小或时长把大文件切成若干段，**不重新编码**，所以切完画质跟原片一模一样，
而且速度只受磁盘 IO 限制——60GB 的文件几分钟就切完，而不是像转码那样要跑几个小时。

### 两种切割模式

| 模式 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **copy**（ffmpeg 流拷贝） | 用 ffmpeg `-c copy` 按关键帧对齐切 | 每段都能**单独播放**，兼容性最好 | 按关键帧对齐，每段实际时长会围绕目标值浮动 |
| **bytes**（纯字节切割） | 直接把原始字节流切成 N 份 | 一个字节都不丢，**拼接回来完全等于原片** | 段边界可能落在帧中间，单段未必能独立播放 |

默认 `auto`：能识别出视频流且 ffmpeg 可用时走 copy，否则自动退回 bytes。

> 相机、运动相机（含大疆）的 MP4 往往带多个附加数据流（遥测、字幕、时间码）。
> 这个工具会自动识别这些流并妥善处理，不会因为「不是标准单流 MP4」而失败。

## 网页控制台

服务起来之后浏览器打开 `http://NAS的IP:8099` 就是控制台，一共五个页面：

- **总览** — 队列状态、处理统计、累计节省的存储
- **任务** — 任务列表、实时进度条、逐任务日志、重试 / 取消 / 删除
- **监控** — 添加要监控的文件夹，立即扫描或等它自动发现
- **定时** — 按 cron 表达式设定时任务，常见场景有预设可选
- **撤销** — 扫描已切分的组，一键把切片删掉、原片改回原名
- **设置** — 分割模式、阈值、原片处理方式、忽略规则、可访问根目录

## 部署方式一：Docker

### 1. 构建并推送镜像（只需要做一次）

镜像支持 **amd64 和 arm64** 双架构——飞牛、群晖、绿联都有 ARM 机型，
推一个多架构 manifest 之后，`docker pull` 在任何机器上都会自动拿到对的那一份。

```bash
DOCKERHUB_USER=你的用户名 ./docker/build-and-push.sh
```

脚本会自动建一个独立的 buildx builder，打上版本号和 `latest` 两个 tag 并推送。
只想本地验证、不推送：

```bash
LOCAL=1 ./docker/build-and-push.sh
```

> 首次构建要拉 node:22-alpine 和 python:3.12-slim 两个基础镜像，会慢一些。
> 需要 docker 支持 buildx（Docker Desktop 自带；Linux 上装 `docker-buildx-plugin`）。

### 2. 在 NAS 上部署

把 `deploy/` 整个目录拷到 NAS，然后：

```bash
cd deploy
cp .env.example .env
vi .env          # 改 VS_IMAGE 为你的镜像地址、PUID/PGID
docker compose up -d
```

`.env` 里各项的含义：

| 变量 | 说明 |
|------|------|
| `VS_IMAGE` | 你的镜像地址，如 `zhangsan/video-splitter:latest` |
| `VS_PORT` | 网页端口，默认 8099 |
| `TZ` | 时区，**会影响定时任务的触发时刻** |
| `PUID` / `PGID` | 容器内进程的属主。SSH 到 NAS 执行 `id 你的用户名` 查 |
| `VS_DATA` | 配置与数据库的存放位置，建议定期备份 |

**关于 PUID / PGID（很重要）**：

容器默认以 root 跑的话，切出来的视频文件属主是 root，在 NAS 的文件管理里会显示成
「不属于任何用户」——既改不了名也删不掉。填成你自己的 uid/gid 就没这个问题。
飞牛默认管理员通常是 `1000:1000`。填 `0` 就是按 root 跑。

### 3. 挂载要监控的目录

`deploy/docker-compose.yml` 默认把 `/vol1` 整盘挂进来：

```yaml
volumes:
  - ${VS_DATA:-./data}:/data
  - /vol1:/vol1
  # 有多个存储空间就继续加
  # - /vol2:/vol2
```

**容器内路径和宿主机保持一致**（左 `/vol1` 右 `/vol1`）是有意的：网页上的
「可访问根目录白名单」默认就是 `/vol1 … /vol4`，保持一致就不用额外配置。
如果有 `/vol2`，加一行挂载、再去网页「设置 → 可访问根目录」里补上 `/vol2` 即可。

## 部署方式二：飞牛 fnOS 应用

`fnos/` 目录是一个完整的 fpk 应用包骨架，比单纯的 Docker 多了这些：

- **桌面图标** — 装完在飞牛桌面点图标直接打开控制台，不用记端口
- **自动识别存储空间** — 安装时按机器上真实存在的 `/vol1`、`/vol2` … 生成挂载列表
  （写死挂载一个不存在的路径，Docker 会凭空建出空目录，把存储空间的显示搞乱）
- **图形化安装向导** — 让用户填挂载路径、UID/GID、时区，不用碰命令行
- **应用中心统一管理** — 启动 / 停止 / 升级 / 卸载都走飞牛自己的流程
- **数据保留策略** — 卸载时可选是否删除配置和任务记录

### 打包

```bash
# 用飞牛官方的 fnpack 工具
fnpack create --template docker video-splitter
```

打包前把镜像地址填好：

- `fnos/app/docker/docker-compose.yaml` 里的 `image`
- 或者打包后在安装时由 `.env` 覆盖

`fnos/manifest` 里的关键字段：

| 字段 | 值 | 说明 |
|------|-----|------|
| `appname` | `video-splitter` | 应用标识 |
| `version` | `1.0.0` | 版本号，升级时递增 |
| `service_port` | `8099` | 网页端口 |
| `platform` | `x86` | 另有 ARM 平台标识 |
| `desktop_uidir` | `ui` | 桌面图标资源目录 |

### 生命周期脚本

`fnos/cmd/` 下的脚本由飞牛在对应时机调用，**全部做成可重入**（应用中心支持重装 / 修复，
同一个脚本会被反复执行）：

| 脚本 | 时机 | 做什么 |
|------|------|--------|
| `install_init` | 安装前 | 检查 docker 是否可用，不满足就报错退出 |
| `install_callback` | 安装后 | 扫描 `/vol[0-9]*` 重写挂载列表、生成 `.env`、预置白名单 |
| `uninstall_init` / `uninstall_callback` | 卸载 | `docker compose down`，按用户选择决定是否删数据 |
| `upgrade_init` / `upgrade_callback` | 升级 | 复用安装逻辑，同时**保留旧的 PUID/PGID** |
| `config_init` / `config_callback` | 配置变更 | 目前是空操作 |

`install_callback` 只重写 `docker-compose.yaml` 里这两行标记**之间**的内容，其余部分保持不动：

```yaml
      # >>> volumes
      - /vol1:/vol1
      # <<< volumes
```

## 核心安全机制：文件稳定检测

这是整个工具最容易被忽略、但最关键的一环。

设想：你在 PC 上往 NAS 拷一个 20GB 的文件，用了十几分钟。如果服务一看到这个文件就
开始切分，它切到的其实是**半个还在写入的文件**——切出来的段全是坏的。

所以文件必须**先证明自己不再被写入**，才会进队列：

- 方式一：文件的修改时间距现在已经超过 `settleSeconds`（默认 60 秒）没有更新；
- 方式二：文件大小连续 `settleSeconds` 秒没有变化。

两者满足其一即可。已经入队等待的文件会被反复复查，确认稳定后才真正开切。
阈值可以按 NAS 的实际情况调：本机磁盘快，调小到 10~15 秒；网络共享目录慢，保持 60 秒甚至调大。

### 目录监控怎么工作

实时监听用 `watchdog`（Linux 下走 inotify）。但 **inotify 在 SMB / NFS 网络共享目录上
是不生效的**——这是个常见坑，很多人以为监控坏了，其实只是内核不会给网络文件系统发事件。

所以有轮询兜底：按 `pollInterval`（默认 30 秒）定期扫描一遍所有监控目录。
即使 inotify 完全失效，也只是发现得慢一点，不会漏。两者互相补充，可以同时开。

## 配置项说明

设置存在数据目录的 `settings.json` 里，网页上改完即时生效。

### 分割

| 项 | 默认 | 说明 |
|----|------|------|
| `mode` | `auto` | `auto` / `copy` / `bytes` |
| `bySize` | `true` | `true` 按大小切，`false` 按时间切 |
| `size` | `3.9G` | 大小阈值，支持 `500M`、`3.9G` 这种写法 |
| `seconds` | `300` | 时间阈值（秒），`bySize=false` 时生效 |
| `all` | `false` | `true` 表示不筛选，所有视频都切 |
| `ext` | 一长串 | 认哪些扩展名 |
| `recursive` | `true` | 是否递归子目录 |
| `outdirMode` | `same` | 切片放原目录，还是统一放指定目录 |
| `markSource` | `rename` | 原片怎么处理，见下表 |
| `sourceDir` | `origin` | `markSource=move` 时移到哪个子目录 |
| `keepMetadata` | `true` | 是否保留拍摄时间等元数据 |
| `overwrite` | `false` | 切片已存在时是否覆盖 |

**`markSource` 的四个取值**：

- `rename` — 原片改名加后缀标记（最安全，出问题能靠撤销还原）
- `move` — 把原片移到 `sourceDir` 子目录
- `none` — 什么都不做，原片原地不动
- `delete` — 切完删掉原片（**不可逆，除非开了回收站**）

### 监控

| 项 | 默认 | 说明 |
|----|------|------|
| `realtime` | `true` | 实时监听，网络共享目录上会自动退化成轮询 |
| `pollInterval` | `30` | 轮询间隔（秒） |
| `settleSeconds` | `60` | 文件稳定检测时长（秒） |
| `minSize` | `0` | 小于该大小的文件忽略 |
| `ignoreSuffixes` | `.tmp` 等 | 正在下载中的临时文件后缀，直接跳过 |
| `allowedRoots` | `/vol1`~`/vol4` | **可访问根目录白名单** |

**关于 `allowedRoots`**：它约束网页上能浏览和添加的目录范围，等于给这个服务划了个圈。
网页上的目录选择器、添加监控目录、扫描接口都会校验这个白名单，越界直接返回 403。
容器里整盘挂载时，填 `/vol1` 这种存储空间根目录。

## 定时任务

用标准 5 段 cron：`分 时 日 月 周`。

```
0 3 * * *        每天凌晨 3 点
0 */6 * * *      每 6 小时一次
30 2 * * 6       每周六凌晨 2:30
```

网页上为每个任务设了「指定监控目录」（留空表示全部）和「启用/停用」开关，
常见场景（每天凌晨 / 每周 / 每小时）有预设，不用自己敲表达式。

时间按容器内时区算，所以 `.env` 里的 `TZ` 要填对，否则「凌晨 3 点」会跑偏。

## 撤销

只要原片是用 `rename` 或 `move` 处理的，就能撤销：

1. 扫描出所有切分过的组；
2. 逐组校验——切片是否齐全、大小对不对、时长是否吻合原片；
3. 通过校验的组，删掉切片、把原片改回原名。

**校验为什么必要**：只按「加起来大小等于原片」判断是不可靠的。
copy 模式按关键帧对齐切，每段实际会比目标多切一点，加起来经常**略大于**原片，
所以判定放宽到 1.5 倍以内，真正的判据是**时长吻合**。

**删除方式**：优先扔进系统回收站而不是直接删除，Linux 下在 NAS 上一般需要
`trash-cli` 或桌面环境支持；不可用时退回直接删除。删完会明确告诉你走的是哪条路。

## 数据与备份

所有持久化都在数据目录里（容器里是 `/data`）：

```
settings.json        切分 / 监控 / 服务参数
watchpoints.json     监控目录列表
schedules.json       定时任务列表
video-splitter.db    SQLite：任务与日志
```

配置项用 JSON 而不是塞进数据库，是因为这几个文件**人能看懂、能手改、能直接拷走备份**。
只有任务流水这种量大、需要按条件查询的数据才值得进数据库。

- 数据库开着 WAL 模式，写入不会阻塞读取；
- 单个任务最多保留 `jobLogLines` 行日志（默认 2000），防止长任务把库撑大；
- 已完成的任务记录保留 30 天，超期自动清理；
- 写配置文件走「临时文件 + 原子替换」，断电或容器被杀不会写坏配置。

**备份**：定期把整个数据目录拷走就行。**迁移**：把数据目录放到新机器的同一位置即可。

## 本地开发

### 后端

```bash
pip install -r requirements.txt
python -m app.main          # 监听 0.0.0.0:8099
```

没有 ffmpeg 也能跑，bytes 模式不依赖它；copy 模式和视频探测需要 ffmpeg 在 PATH 里。

### 前端

```bash
cd web
npm install
npm run dev                 # 开发服务器，带热更新，代理到后端
npm run build               # 产出 web/dist
npm run build               # 注意：build 会先跑 vue-tsc 类型检查，类型错误会中断构建
```

前端构建产物由后端进程直接托管（`app/main.py` 挂载 `web/dist`），
所以**整个服务只有一个端口、一个容器，不需要额外的 nginx**。
前端没构建时后端也能起，只是访问 `/` 会给一句提示，方便单独调后端。

### 端到端冒烟测试

```bash
python tools/smoke_test.py
```

真起一个服务进程（端口 8123），用真实 ffmpeg 造个小视频，把整条链路跑一遍：

```
健康检查 → 改设置 → 添加监控目录 → 扫描入队 → 等任务完成
→ 查日志 → 撤销预览 → 真正撤销 → 校验切片已删、原片改名已还原
```

会在项目下建 `.tmp-test/` 目录，测完可以整个删掉。

### 重新生成图标

```bash
python tools/make_icons.py
```

纯标准库（zlib + struct）手写 PNG，不依赖 Pillow，4 倍超采样抗锯齿。

## 常见问题

**切片文件在 NAS 文件管理里改不动、删不掉？**
`PUID` / `PGID` 没填对，文件属主是 root。改 `.env` 里的这两个值重启容器。

**新拷进来的文件没被自动发现？**
先看是不是网络共享目录（SMB/NFS）——inotify 在那里不生效，得靠轮询，
检查 `pollInterval` 是不是设得太长。其次看文件是不是还没稳定，`settleSeconds` 默认 60 秒，
大文件在拷完 60 秒后才会进队列。

**切完的段加起来比原片大？**
正常现象。copy 模式按关键帧对齐，每段会多切一点，所以合计略大于原片。撤销时已考虑这种情况。

**某个视频切分失败？**
看该任务的日志。常见原因是文件本身损坏、或者不支持的编码。
把 `mode` 切到 `bytes` 通常能绕过——bytes 不解析视频结构，只切字节流。

**想先试一下再正式跑？**
设置里有 `debug` 开关，打开后只打印将要做什么、不实际动手。

**端口 8099 被占用？**
改 `.env` 的 `VS_PORT`。

## 技术选型说明

| 选择 | 原因 |
|------|------|
| FastAPI 而非 Flask | 需要 WebSocket 推实时进度与日志，FastAPI 原生支持 async WebSocket |
| SQLite 而非 PostgreSQL | NAS 上多一个数据库服务是负担；单机单进程场景 SQLite 完全够，WAL 模式读写不互斥 |
| JSON 存配置而非数据库 | 配置要能手改、能直接备份、升级时能自动补默认值 |
| 单并发 worker | 切分是磁盘 IO 密集任务，并发跑多个只会让 NAS 磁盘来回寻道、整体更慢 |
| 前端构建产物由后端托管 | 一个端口一个容器，用户不用再配 nginx，也不用理解反向代理 |
| watchdog + 轮询双保险 | inotify 在网络共享目录上不生效，必须有兜底 |
| 镜像内置 ffmpeg | 让用户自己装 ffmpeg 是部署失败的最大来源 |
| gosu 而非 USER 指令 | 需要在启动时把挂载目录 chown 成 PUID 之后才降权，USER 指令做不到 |
