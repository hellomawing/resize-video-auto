# 视频无损分割 · NAS 版

把超大视频切成多段，**全程不重新编码**，画质音质零损失。给 NAS 用：加几个监控文件夹，
新拷进来的视频自动发现并处理；也能按「每隔几小时 / 每天几点」排定时扫描。所有参数都在网页上改。

支持两种部署形态：**Docker** 和 **飞牛 fnOS 应用（fpk）**。

---

## 它解决什么问题

相机、运动相机、无人机拍出来的单个文件动辄 10~60GB，拷进 NAS 之后：

- 手机、电视、剪辑软件打不开这么大的文件；
- 想传给别人，单个文件太大传不动；
- 有些平台对单文件大小有限制。

这个工具按大小或时长把大文件切成若干段，**不重新编码**，所以切完画质跟原片一模一样，
而且速度只受磁盘 IO 限制——60GB 的文件几分钟就切完，而不是像转码那样要跑几个小时。

### 两种切割模式

| 模式 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **copy**（ffmpeg 流拷贝） | 用 ffmpeg `-c copy` 按关键帧对齐切 | 每段都能**单独播放**，兼容性最好 | 按关键帧对齐，每段实际时长会围绕目标值浮动 |
| **bytes**（纯字节切割） | 直接把原始字节流切成 N 份 | 一个字节都不丢，**拼接回来完全等于原片** | 段边界可能落在帧中间，单段未必能独立播放 |

默认 `auto`：能识别出视频流且 ffmpeg 可用时走 copy，否则自动退回 bytes。

copy 模式的写法值得说一句：分段**先写进一个临时工作目录**，全部切完并校验通过后，
再改名成最终文件名。这样是「要么整套切片都在、要么一个都没有」，不会留下半套切片。

这个工作目录会**优先建在输出目录的同一个文件系统上**——不是讲究：跨文件系统的改名
会退化成真正的拷贝，整套切片要多读一遍多写一遍。在一块普通机械盘上，这会让一次
6.5G 的切分从约 2 分钟变成 4 分半，一半时间纯粹花在搬数据上。

> 相机、运动相机（含大疆）的 MP4 往往带多个附加数据流（遥测、字幕、时间码）。
> 这个工具会自动识别这些流并妥善处理，不会因为「不是标准单流 MP4」而失败。

## 网页控制台

服务起来之后浏览器打开 `http://NAS的IP:8099` 就是控制台，一共五个页面：

- **总览** — 队列状态、处理统计、累计节省的存储；「立即扫描」旁可临时指定这一次原片怎么处理
- **任务** — 任务列表、实时进度条、逐任务日志、重试 / 取消 / 删除
- **监控** — 添加要监控的文件夹，选择扫描方式（实时 / 每隔几小时 / 每天 / 仅手动），
  以及每个目录自己的原片处理方式
- **撤销** — 扫描已切分的组，一键把切片删掉、原片改回原名
- **设置** — 分割模式、阈值、原片处理方式（默认值）、忽略规则、可访问根目录

## 先选一条路

| | 方式一：Docker | 方式二：飞牛 fnOS 应用（fpk） |
|---|---|---|
| 适合 | **想快点跑起来**，或者手上不是飞牛 | 飞牛用户，想要桌面图标和应用中心统一管理 |
| 操作 | 改两个文件 → `docker compose up -d` | 装 fnpack → `fnpack build` → 装 fpk |
| 得到 | 一个容器，浏览器按 `IP:8099` 打开 | 桌面出现「视频分割」图标，点开即用 |

两种方式跑的是**同一个镜像**，功能完全一样。飞牛用户建议先走方式一确认能跑通，
再打包成 fpk——这样出问题时容易定位是镜像的问题还是包的问题。

## 部署方式一：Docker

> 飞牛 fnOS 用户同样适用：飞牛自带 Docker，SSH 上去按下面的步骤做即可，
> 不一定非要打成 fpk。

### 1. 构建并推送镜像（只需要做一次）

镜像支持 **amd64 和 arm64** 双架构。推一个多架构 manifest 之后，`docker pull` 会按机器
自动选对的那一份，x86 与 ARM 的 NAS 不用分别维护镜像。

```bash
DOCKERHUB_USER=你的用户名 ./docker/build-and-push.sh
```

脚本会自动建一个独立的 buildx builder，打上版本号和 `latest` 两个 tag 并推送。
只想本地验证、不推送：

```bash
LOCAL=1 ./docker/build-and-push.sh
```

> 首次构建要拉 node:22-alpine 和 python:3.12-slim 两个基础镜像，会慢一些。
> 需要 docker 支持 buildx（Docker Desktop 自带；Linux 上装 `docker-buildx-plugin`）。

### 1-B. 如果 NAS 连不上 Docker Hub：改成在 NAS 上直接构建

**国内不少 NAS 是访问不了 `registry-1.docker.io` 的**（实测某台飞牛就是这样，
`curl https://registry-1.docker.io/v2/` 直接超时），但本地 `daemon.json` 里配了
国内镜像源。这种情况下「本地 push → NAS pull」这条路走不通，直接在 NAS 上构建反而
更省事：不用传镜像，也不用给 NAS 开外网。

前提是 NAS 的基础镜像能通过镜像源拉到（`/etc/docker/daemon.json` 里的
`registry-mirrors`）。先验一下：

```bash
docker pull python:3.12-slim-bookworm
docker pull node:22-alpine
```

两个都能下就没问题。然后把源码打包传上去构建：

```bash
# ① 本地：打一个干净的源码包（不含 node_modules 和 dist，几十 KB）
tar -czf /tmp/vs-src.tar.gz \
  --exclude='web/node_modules' --exclude='web/dist' --exclude='__pycache__' \
  app core docker web requirements.txt

# ② 传到 NAS
scp -P 7788 /tmp/vs-src.tar.gz admin@NAS_IP:/vol1/1000/video-splitter/src.tar.gz

# ③ NAS 上：解包并构建
cd /vol1/1000/video-splitter && tar -xzf src.tar.gz -C src && cd src
docker build -f docker/Dockerfile -t video-splitter:1.0.0 .
```

构建完镜像名就是 `video-splitter:1.0.0`，`deploy/.env` 里的 `VS_IMAGE` 照抄即可，
不需要 `docker login`。

> **构建要通过 SSH 跑很久，注意别让它被断开带走。** 直接 `ssh nas "docker build ..."`
> 挂在前台时，一旦连接中断构建就一起没了。用 `setsid` 脱离会话：
>
> ```bash
> setsid bash -c 'docker build -f docker/Dockerfile -t video-splitter:1.0.0 . \
>   > ../build.log 2>&1' < /dev/null > /dev/null 2>&1 &
> ```
>
> 关键是**三个 fd 都要重定向掉**。少重定向 stdin 的话，`docker build` 会占住
> SSH 通道的 stdin，导致 sshd 不认为会话结束、本地命令一直不返回。
> 之后用 `tail -f ../build.log` 看进度。
>
> 受镜像源速度影响，ffmpeg 那一步（Debian 上依赖链很长）可能要 10 分钟以上，
> 耐心等。构建有分层缓存，中途失败重跑不会从头再来。

> ⚠️ **构建上下文放在 NAS 共享目录里时，注意权限位这个坑。**
> 实测飞牛 `/vol1/1000/**` 下的文件，经典权限位是 `000`（真实访问靠 ACL，
> 所以平时读写都正常）。而 `docker COPY` 会**原样保留这个 000**，镜像里的代码
> 就变成 root 可读、其它用户全不可读，entrypoint 按 PUID 降权后直接
> `PermissionError`，容器无限重启。本仓库的 Dockerfile 里已经用
> `RUN chmod -R a+rX ...` 兜住了，所以直接构建不会有问题；
> 但如果你自己另写 Dockerfile，记得做同样的事。
>
> 判断方法：`docker run --rm --entrypoint sh 镜像名 -c 'ls -la /opt/video-splitter/app'`，
> 看到 `----------` 就是中招了。

### 1-C. 以后更新版本：一条命令

上面那串手工步骤已经固化成了脚本，改完代码重新部署只要跑它：

```bash
python tools/deploy_nas.py
```

它会：打源码包 → 上传 → **先删旧源码再解包** → 检查有没有正在跑的任务 →
构建 → `--force-recreate` 重建容器 → 等健康检查通过。

> 为什么要「先删再解包」：直接覆盖的话，你本地删掉的文件会永远留在 NAS 上，
> 而且照样被 `COPY` 进镜像，症状是「改了却没生效」，极难查。

| 参数 | 用途 |
|---|---|
| `--skip-build` | 只重建容器，不重新构建镜像（改了 `deploy/` 时才这么用） |
| `--wait 300` | 有任务在跑时最多等 300 秒。**重建会掐断跑着的任务** |
| `--force` | 不管有没有任务在跑，直接重建 |
| `--dry-run` | 只打包并打印将要执行的命令，不连 NAS |
| `--remote DIR` | 部署根目录，默认 `/vol1/1000/video-splitter` |
| `--port N` | 容器端口，默认 `8099`（用于查任务和健康检查） |

首次全新构建约 19 分钟（几乎全耗在 Debian 装 ffmpeg 的依赖链上），之后只改应用层
代码时 apt / pip / 前端依赖全部命中缓存，**1~3 分钟**就完事——别按 19 分钟预估而不敢动。

> `deploy/` **不在源码包里**，所以 NAS 上的 `src/deploy/.env` 不会被覆盖，脚本也不会
> 删它。里面的 `PGID` 经常和 `PUID` 不一样（实测这台飞牛是 `1000:1001`）。
>
> 凭据放在 `deploy/.nas-credentials`（`KEY=VALUE` 格式，已被 `.gitignore` 排除），
> 所以装好一次之后就不用每次 `export` 了。临时换一台机器时用环境变量覆盖即可，
> 环境变量优先级更高。
>
> ⚠️ 该文件里是**明文密码**。开源 / 发布前要删掉它并轮换 NAS 密码——
> 清单见 `OPEN-SOURCE-CHECKLIST.md`，机械自检跑 `python tools/check_release_ready.py`。

### 2. 在 NAS 上部署

把 `deploy/` 整个目录拷到 NAS，然后：

```bash
cd deploy
cp .env.example .env
vi .env          # 改 VS_IMAGE 为你的镜像地址、PUID/PGID
docker compose up -d
```

`.env` 里各项的含义：

| 变量 | 说明 |
|------|------|
| `VS_IMAGE` | 你的镜像地址，如 `zhangsan/video-splitter:latest` |
| `VS_PORT` | 网页端口，默认 8099 |
| `TZ` | 时区，**会影响「每隔几小时 / 每天几点」的触发时刻** |
| `PUID` / `PGID` | 容器内进程的属主。SSH 到 NAS 执行 `id 你的用户名` 查 |
| `VS_DATA` | 配置与数据库的存放位置，建议定期备份 |

**关于 PUID / PGID（很重要）**：

容器默认以 root 跑的话，切出来的视频文件属主是 root，在 NAS 的文件管理里会显示成
「不属于任何用户」——既改不了名也删不掉。填成你自己的 uid/gid 就没这个问题。

**注意 gid 往往不等于 uid**，`id 你的用户名` 输出里的两项都要看：

```
$ id admin
uid=1000(admin) gid=1001(Users) groups=1001(Users),994(docker),1000(Administrators)
      ↑ PUID 填这个        ↑ PGID 填这个
```

实测飞牛 fnOS 的 admin 是 `1000:1001`（`Users` 组是 1001），群晖常见 `1026:100`。
填 `0` 就是按 root 跑。

> 填错不会报错，只会让文件属主不对。容器启动时会拿挂载卷的属组和 `PGID` 比一下，
> 对不上直接在日志里提示该填多少，`docker logs video-splitter` 能直接看到。

### 3. 挂载要监控的目录

`deploy/docker-compose.yml` 默认把 `/vol1` 整盘挂进来：

```yaml
volumes:
  - ${VS_DATA:-./data}:/data
  - /vol1:/vol1
  # 有多个存储空间就继续加
  # - /vol2:/vol2
```

**容器内路径和宿主机保持一致**（左 `/vol1` 右 `/vol1`）是有意的：网页上的
「可访问根目录白名单」默认就是 `/vol1 … /vol4`，保持一致就不用额外配置。
如果有 `/vol2`，加一行挂载、再去网页「设置 → 可访问根目录」里补上 `/vol2` 即可。

## 部署方式二：飞牛 fnOS 应用

`fnos/` 目录是一个完整的 fpk 应用包骨架，比单纯的 Docker 多了这些：

- **桌面图标** — 装完在飞牛桌面点图标直接打开控制台，不用记端口
- **自动识别存储空间** — 安装时按机器上真实存在的 `/vol1`、`/vol2` … 生成挂载列表
  （写死挂载一个不存在的路径，Docker 会凭空建出空目录，把存储空间的显示搞乱）
- **图形化安装向导** — 让用户填挂载路径、UID/GID、时区，不用碰命令行
- **应用中心统一管理** — 启动 / 停止 / 升级 / 卸载都走飞牛自己的流程
- **数据保留策略** — 卸载时可选是否删除配置和任务记录

### 前提：先把镜像推上去

fpk 包里只有编排文件和脚本，容器镜像要从 Docker Hub 拉，所以先做一次多架构构建推送：

```bash
DOCKERHUB_USER=你的用户名 ./docker/build-and-push.sh
```

再把镜像地址填进 `fnos/app/docker/docker-compose.yaml` 的 `image`。这一项**必须手改**：
留着 `yourname/...` 占位的话，`cmd/install_init` 会在安装第一步就拦下来并提示你
（总比装完卡在拉不到镜像、甩一段 docker 英文报错要好）。

### 打包

`fnos/` 已经是一个**完整的应用包**，**不需要**再执行 `fnpack create`——那个命令是用来
从模板新建空项目的，在本项目上跑只会平白多出一份用不上的骨架。

1）下载官方 `fnpack`（当前 1.2.3，按开发机的系统选一个）：

| 系统 | 文件 |
|------|------|
| Windows x86 | `fnpack-1.2.3-windows-amd64` |
| Linux x86 | `fnpack-1.2.3-linux-amd64` |
| Linux ARM | `fnpack-1.2.3-linux-arm64` |
| macOS Intel | `fnpack-1.2.3-darwin-amd64` |
| macOS Apple Silicon | `fnpack-1.2.3-darwin-arm64` |

下载地址：<https://developer.fnnas.com/docs/cli/fnpack>

Linux / macOS 装到系统路径：

```bash
chmod +x fnpack-1.2.3-linux-amd64
sudo mv fnpack-1.2.3-linux-amd64 /usr/local/bin/fnpack
fnpack --help
```

2）打包。在应用目录里执行，产物是 `video-splitter.fpk`：

```bash
cd fnos
fnpack build
```

`fnpack` 在生成 `.fpk` 前会校验必要文件，本包应当全部通过：`manifest`、
`config/privilege`、`config/resource`、`ICON.PNG`、`ICON_256.PNG`、`app/`、`cmd/`、
`wizard/`，以及 `app/ui/`（因为 manifest 里声明了 `desktop_uidir=ui`）。

> 本包已用官方 `fnpack` 1.2.3 实际打包验证通过，产物约 14 KB。
> 打出来的 `.fpk` 是 gzip 过的 tar，里面是 `manifest`、`config/`、`cmd/`、`wizard/`、
> 两个 `ICON*.PNG`，以及 `app.tgz`（内含 `docker/docker-compose.yaml` 和 `ui/`）。

3）装到 NAS 上：

```bash
# 方式一：命令行（推荐）
appcenter-cli install-fpk video-splitter.fpk
```

方式二：应用中心 → 手动安装。手动安装入口**默认是关闭的**，需要先在 NAS 上 SSH 执行：

```bash
appcenter-cli manual-install enable
```

> 飞牛官方提示：手动安装入口仅用于应用测试，不得用于应用分发。

安装后应用目录在 `/var/apps/video-splitter`，安装脚本的日志在
`/var/apps/video-splitter/var/install.log`。

`fnos/manifest` 里的关键字段：

| 字段 | 值 | 说明 |
|------|-----|------|
| `appname` | `video-splitter` | 应用唯一标识，也是安装目录名 |
| `version` | `1.0.0` | 版本号，升级时递增 |
| `display_name` | `视频无损分割` | 应用中心里显示的名字 |
| `source` | `thirdparty` | 第三方应用固定填这个 |
| `platform` | `all` | `x86` / `arm` / `all` |
| `service_port` | `8099` | 网页端口 |
| `desktop_uidir` | `ui` | 桌面入口目录 |
| `desktop_applaunchname` | `video-splitter.main` | 点应用卡片时打开哪个入口 |
| `ctl_stop` | `true` | 应用中心里显示启动 / 停止 |
| `disable_authorization_path` | `true` | 隐藏飞牛的「授权目录」设置 |

两点说明：

- **`platform=all`**：本包内只有 JSON / YAML / bash 脚本和 PNG，不含任何架构相关二进制，
  架构差异全部由多架构镜像承担，所以按官方定义应该填 `all`。前提是镜像确实推成多架构——
  如果你只用 `LOCAL=1` 构建过 amd64，请把这里改回 `x86`，否则 ARM 机器能装上却拉不到镜像。
- **`disable_authorization_path=true`**：本应用的目录权限由自带的「可访问根目录白名单」+
  compose 里的挂载共同决定，不再依赖飞牛的授权目录机制。若你希望改回由飞牛管授权目录，
  把这项改成 `false`。

### 生命周期脚本

`fnos/cmd/` 下的脚本由飞牛在对应时机调用，**全部做成可重入**（应用中心支持重装 / 修复，
同一个脚本会被反复执行）：

| 脚本 | 时机 | 做什么 |
|------|------|--------|
| `install_init` | 安装前 | 检查 docker 是否可用、镜像地址是否已改，不满足就报错退出 |
| `install_callback` | 安装后 | 扫描 `/vol[0-9]*` 重写挂载列表、生成 `.env`、预置白名单 |
| `uninstall_init` / `uninstall_callback` | 卸载 | `docker compose stop/down`，按用户选择决定是否删数据 |
| `upgrade_init` / `upgrade_callback` | 升级 | 复用安装逻辑，同时**保留旧的 PUID/PGID** |
| `config_init` / `config_callback` | 配置变更 | 目前是空操作 |

### 安装向导

`wizard/install` 里收集三个值，卸载向导收集一个：

| 向导字段 | 变成的环境变量 | 用途 |
|----------|----------------|------|
| `wizard_mount_paths` | `wizard_mount_paths` | 除存储空间外额外挂载的路径（可选，逗号分隔） |
| `wizard_puid` / `wizard_pgid` | 同名 | 容器内进程属主，写进 `.env` 的 `PUID` / `PGID` |
| `wizard_timezone` | `wizard_timezone` | 写进 `.env` 的 `TZ`，决定定时扫描按哪个时区触发 |
| `wizard_remove_data` | `wizard_remove_data` | 卸载时是否连同配置与任务记录一起删掉 |

两个容易踩的坑，改向导时务必注意：

- **字段名就是环境变量名**，两者必须完全一致。`install_callback` 读的是 `wizard_puid`，
  所以字段也必须叫 `wizard_puid`——名字对不上向导收集的值会被静默忽略、一直用兜底默认值，
  而且**不会报任何错**，很难发现。
- **`rules` 是数组**，不是对象。`{"rules": {"required": true}}` 会打包失败；
  正确写法是 `{"rules": [{"required": true, "message": "..."}]}`。
  另外 `switch` 类型的 `initValue` 要写字符串 `"false"`，写布尔 `false` 同样过不了校验。

`install_callback` 只重写 `docker-compose.yaml` 里这两行标记**之间**的内容，其余部分保持不动：

```yaml
      # >>> volumes
      - /vol1:/vol1
      # <<< volumes
```

## 核心安全机制：文件稳定检测

这是整个工具最容易被忽略、但最关键的一环。

设想：你在 PC 上往 NAS 拷一个 20GB 的文件，用了十几分钟。如果服务一看到这个文件就
开始切分，它切到的其实是**半个还在写入的文件**——切出来的段全是坏的。

所以文件必须**先证明自己不再被写入**，才会进队列：

- 方式一：文件的修改时间距现在已经超过 `settleSeconds`（默认 60 秒）没有更新；
- 方式二：文件大小连续 `settleSeconds` 秒没有变化。

两者满足其一即可。已经入队等待的文件会被反复复查，确认稳定后才真正开切。
阈值可以按 NAS 的实际情况调：本机磁盘快，调小到 10~15 秒；网络共享目录慢，保持 60 秒甚至调大。

### 目录监控怎么工作

实时监听用 `watchdog`（Linux 下走 inotify）。但 **inotify 在 SMB / NFS 网络共享目录上
是不生效的**——这是个常见坑，很多人以为监控坏了，其实只是内核不会给网络文件系统发事件。

所以有轮询兜底：按 `pollInterval`（默认 30 秒）定期扫描一遍所有监控目录。
即使 inotify 完全失效，也只是发现得慢一点，不会漏。两者互相补充，可以同时开。

### 扫描方式

每个监控目录各自选一种扫描方式，一个字段同时回答「要不要自动扫」「多久扫一次」：

| 扫描方式 | 行为 | 适合 |
|---|---|---|
| 实时监听 | 文件一落盘就被发现并切分，含上面的轮询兜底 | 相机、下载器直接写入的目录 |
| 每隔几小时 | 每 1/2/3/4/6/8/12/24 小时扫一次（从每天 0 点起算） | 白天陆续有文件、想攒一攒再处理 |
| 每天定时 | 每天某个时刻扫一次，如 03:00 | 夜间批处理，白天不占 IO |
| 仅手动 | 不自动扫描，只在你点「扫描」时才处理 | 想完全自己把握时机 |

为什么是一个下拉而不是「启用 + 自动扫描」两个开关：两个开关会组合出
「启用了但不自动扫」这种需要停下来想一下的状态。早期版本正是用一个「启用」
同时管着自动扫描和手动扫描，结果用户取消勾选后连手动扫描都点不动了。

**自动扫描和手动扫描是两条独立的路**：上面这张表约束的是**自动**扫描；
而监控目录列表里那个「扫描」按钮、总览页的「立即扫描」，**任何时候都能点**，
不受扫描方式限制——你既然亲手按了按钮，就不该被「仅手动」之类的设置拦住。

「每隔几小时」只提供 1/2/3/4/6/8/12/24 这几个档位，是因为它最终翻译成
`0 */N * * *` 这样的 cron 表达式，只有 N 能整除 24，「每 N 小时」才能从 0 点起
均匀铺满一天、不留空档；换来的是容器重启不会打乱节奏，界面上也能准确预告
「下次扫描时间」。

按时间触发的计划用的是**容器内时区**，所以 `.env` 里的 `TZ` 要填对，
否则「每天凌晨 3 点」会跑偏。

### 目录里明明有视频，扫描却说「没有需要处理的新视频」

这几乎总是同一个原因：那些文件是**本工具自己产生的**——切片叫 `xxx#1.MP4`，
切过的原片叫 `xxx#origin.MP4`。扫描器会**刻意跳过**它们，因为不跳过的后果
是把自己切出来的半成品再切一遍，数据就废了。

跳过本身是对的，但「默默跳过」会让你无从判断到底是真没有、还是被跳过了。
所以扫描结果会如实说清楚，而且**把两种相反的状态分开讲**：

| 目录里有什么 | 意味着 | 扫描会怎么说 |
|---|---|---|
| `xxx#1.MP4` 等切片 | 正常产物 | 已跳过 |
| `xxx#origin.MP4`，切片还在 | 这次切分是完整的 | 已跳过 |
| `xxx#origin.MP4`，**切片不在了** | 分割结果被删或搬走，原片可以重切 | 「**可以重新分割**」，并弹窗问要不要现在重切 |

第三种最容易被误读：它挂着 `#origin` 看着像「已经处理完了」，其实这次切分的
结果早就没了。以前它和普通跳过共用一句话，你根本看不出「这个还能救」。

如果你把原片处理方式设成了 `move`，原片会被搬到同级的归档子文件夹
（默认 `resize-video-origin-file/`）。扫描器会把归档目录**整体排除**，
所以搬过去的原片也不会被重切——但代价是**归档目录里的文件不会再被扫描**，
别把想处理的视频放进去。

排除是**按位置判断的**：只有落在本次扫描范围**之内**、且路径上某一层目录名撞上的
文件才算归档。所以归档目录取成 `1000`、`vol1` 这类「路径上本来就有的段名」也不会
误伤——早期版本比的是绝对路径的每一段，归档目录一旦叫 `1000`，监控目录下的文件
会**全部**被判成「位于原片归档目录」，表现就是扫描永远发现 0 个视频，而给的理由
看着还挺合理，极难联想到是名字撞的。唯一的例外是取成**监控目录自己的名字**：
那整个扫描范围确实都在它「里面」。

顺带一提，早期版本的归档目录叫 `origin`。升级后配置里的这个名字会被**自动迁到
新默认名**，而 `origin` 目录本身仍会被扫描器排除，所以老数据不用手动搬。

**归档目录名是「用过就记住」的。** 排除用的候选名不只取当前配置，还包括**曾经用过
的名字**（记在 `data/archive-dirs.json`，只增不减）。原因是 `move` 归档过去的原片
**保留着原文件名**，而排除集如果只按当前配置现算，你把归档目录改个名、或者清空回
「跟随系统」，旧名字立刻掉出集合——躺在旧目录里的原片看上去就是个新视频，会被重切
一遍再标记一次（真机复现过）。方向刻意偏向「多排除」：多排除顶多漏扫，漏排除会让
原片和切片一起报废。代价是这个名字集合只增不减，真想让某个名字放行，得手工编辑
`archive-dirs.json` 再重启服务（进程内有一份缓存，改文件不会立刻生效）。

```
扫描完成：没有需要处理的新视频。目录里有 1 个原片的分割结果已经不在
（切片被删除或移走），可以重新分割。
```

点弹窗里的**「恢复并重新分割」**，工具会把原片名改回去、立刻重扫一遍。
不想当场重切也行：去**「撤销分割」页**那个专门的区块点「恢复原名」，
它会变回待处理的普通文件，你自己挑时间点扫描。

## 配置项说明

设置存在数据目录的 `settings.json` 里，网页上改完即时生效。

### 分割

| 项 | 默认 | 说明 |
|----|------|------|
| `mode` | `auto` | `auto` / `copy` / `bytes` |
| `bySize` | `true` | `true` 按大小切，`false` 按时间切 |
| `size` | `3.9G` | 大小阈值，支持 `500M`、`3.9G` 这种写法 |
| `seconds` | `300` | 时间阈值（秒），`bySize=false` 时生效 |
| `all` | `false` | `true` 表示不筛选，所有视频都切 |
| `ext` | 一长串 | 认哪些扩展名 |
| `recursive` | `true` | 是否递归子目录 |
| `outdirMode` | `same` | 切片放原目录，还是统一放指定目录 |
| `markSource` | `rename` | 原片怎么处理，见下 |
| `sourceDir` | `resize-video-origin-file` | `markSource=move` 时移到哪个子目录 |
| `keepMetadata` | `true` | 是否保留拍摄时间等元数据 |
| `overwrite` | `false` | 切片已存在时是否覆盖 |

**`markSource` 的四个取值**：

| 值 | 原片去哪 | 风险 |
|----|---------|------|
| `rename` | 改名加 `#origin` 后缀，留在原地 | 无（最安全，出问题能靠撤销还原） |
| `move` | 移到同级的 `sourceDir` 子目录 | 无（归档目录名会被扫描器排除） |
| `none` | 原地不动、一个字都不改 | ⚠️ 下次扫描会把它**当新视频再切一遍** |
| `delete` | 切完删掉 | ⚠️ **不可逆**（容器里没有回收站，就是直接删） |

**这三个设置能在三个地方设，前一级压过后一级**：

| 级别 | 在哪设 | 作用范围 |
|------|--------|----------|
| 1 | 手动扫描时临时指定（点「扫描」旁边那个下拉框） | **只影响这一次**，不落盘 |
| 2 | 每个监控目录自己的「原片处理」列 | 该目录扫出来的所有任务 |
| 3 | 系统设置（上面的 `markSource` / `sourceDir`） | 全局默认值 |

监控目录那一级留「跟随系统设置」就是空串——这是**有意的未设置状态**，不是缺省值，
所以升级之后老配置不会被写死成某个具体值。

**改设置只影响之后入队的任务**：处理方式在入队那一刻就写进任务记录（快照），
执行时不再回头读设置。否则任务在队列里排队时你改一次设置，
排在后面的任务会换一套行为，「同一个目录扫出来的两批任务处理方式不一样」没法解释。
「重试」也沿用原任务的快照。

### 监控

| 项 | 默认 | 说明 |
|----|------|------|
| `realtime` | `true` | 实时监听，网络共享目录上会自动退化成轮询 |
| `pollInterval` | `30` | 轮询间隔（秒） |
| `settleSeconds` | `60` | 文件稳定检测时长（秒） |
| `minSize` | `0` | 小于该大小的文件忽略 |
| `ignoreSuffixes` | `.tmp` 等 | 正在下载中的临时文件后缀，直接跳过 |
| `allowedRoots` | `/vol1`~`/vol4` | **可访问根目录白名单** |

**关于 `allowedRoots`**：它约束网页上能浏览和添加的目录范围，等于给这个服务划了个圈。
网页上的目录选择器、添加监控目录、扫描接口都会校验这个白名单，越界直接返回 403。
容器里整盘挂载时，填 `/vol1` 这种存储空间根目录。

## 撤销

只要原片是用 `rename` 或 `move` 处理的，就能撤销：

1. 扫描出所有切分过的组；
2. 逐组校验——切片是否齐全、大小对不对、时长是否吻合原片；
3. 通过校验的组，删掉切片、把原片改回原名。

**校验为什么必要**：只按「加起来大小等于原片」判断是不可靠的。
copy 模式按关键帧对齐切，每段实际会比目标多切一点，加起来经常**略大于**原片，
所以判定放宽到 1.5 倍以内，真正的判据是**时长吻合**。

> ⚠️ **实测发现的一个坑：撤销的目标目录如果同时是监控目录，原片会被立刻重新切一遍。**
>
> 防重复处理的机制是隐式的——切完把源文件改名成 `#origin`，原路径不再匹配，自然就不会重复切。
> 而撤销干的正是把这个改名还原，于是这道防线一并消失。实测：撤销后 37 秒，
> 监控目录就把恢复出来的原片又切了一次，看上去像「撤销没生效」。
>
> 规避：撤销前先在网页上把这个监控目录的扫描方式改成**「仅手动」**，恢复完再改回去。
> 这种目录干脆常驻「仅手动」、需要时手动点扫描，会更省心。
>
> 反过来说，这个行为有时正是你想要的——切片误删了想重切，就在「撤销分割」页
> 「切片已不在的原片」那一栏点「恢复原名」。根本修法（给扫描器加「已处理过」的
> 记录）见下方备注。

**删除方式**：优先扔进系统回收站而不是直接删除，Linux 下在 NAS 上一般需要
`trash-cli` 或桌面环境支持；不可用时退回直接删除。删完会明确告诉你走的是哪条路。
（容器镜像里没装回收站工具，所以走的是直接删除，返回信息里会写明
「当前环境没有可用的回收站」。）

## 数据与备份

所有持久化都在数据目录里（容器里是 `/data`）：

```
settings.json        切分 / 监控 / 服务参数
watchpoints.json     监控目录列表（含各自的扫描方式）
archive-dirs.json    用过的归档子目录名（只增不减，见「原片处理方式」）
video-splitter.db    SQLite：任务与日志
```

配置项用 JSON 而不是塞进数据库，是因为这几个文件**人能看懂、能手改、能直接拷走备份**。
只有任务流水这种量大、需要按条件查询的数据才值得进数据库。

这几份 JSON 都可以直接备份和搬走（换机器时整个数据目录拷过去即可），
但 `archive-dirs.json` 要**连老的一起带**：它是「哪些目录名算归档」的依据，
丢了就等于把老归档目录里的原片重新暴露给扫描器。

- 数据库开着 WAL 模式，写入不会阻塞读取；
- 单个任务最多保留 `jobLogLines` 行日志（默认 2000），防止长任务把库撑大；
- 已完成的任务记录保留 30 天，超期自动清理；
- 写配置文件走「临时文件 + 原子替换」，断电或容器被杀不会写坏配置。

**备份**：定期把整个数据目录拷走就行。**迁移**：把数据目录放到新机器的同一位置即可。

## 常见问题

**切片文件在 NAS 文件管理里改不动、删不掉？**
`PUID` / `PGID` 没填对，文件属主是 root。改 `.env` 里的这两个值重启容器。

**新拷进来的文件没被自动发现？**
先看是不是网络共享目录（SMB/NFS）——inotify 在那里不生效，得靠轮询，
检查 `pollInterval` 是不是设得太长。其次看文件是不是还没稳定，`settleSeconds` 默认 60 秒，
大文件在拷完 60 秒后才会进队列。

**切完的段加起来比原片大？**
正常现象。copy 模式按关键帧对齐，每段会多切一点，所以合计略大于原片。撤销时已考虑这种情况。

**切一个 6G 的片子要几分钟，正常吗？为什么不是「秒切」？**
正常，在这类硬件上就是这个速度。「无损」省掉的是**解码 / 编码（CPU）**，但**数据的
读写量一字节都省不掉**：源文件要完整读一遍，切片要完整写一遍，6.5G 的片子就是约
12.6GB 的磁盘读写。单块机械盘只有 100~150MB/s，所以两分钟上下就是物理下限——
想更快只能上 SSD，或让源目录和输出目录落在不同物理盘上。
另外，切分中途的临时文件也在同一块盘上，所以临时目录一旦跨了文件系统，还会**再白搬一遍**
（见「两种切割模式」一节），那才是可以避免的浪费。

**选目录时只能点进根目录，一点就提示「没有权限」、再也走不下去？**
这是 fnOS 这类系统的正常行为，不是你配错了。它们把存储池根目录（`/vol1`）的权限位设成
`000`、连一条扩展 ACL 都没有，**故意不让普通用户枚举它**——所以「从根往下逐级点」在
第一级就断了。但**能不能枚举和能不能访问是两回事**：`/vol1/1000` 及其下的目录完全正常。

选择器里有两条绕过去的路：

- **常用目录**：点一下直达。列表里是你**已经添加过的监控目录**、**最近任务处理过的目录**、
  以及**设置里的输出目录**——撤销和重新分割想找的地方基本都在这儿。
- **直接输入完整路径**，例如 `/vol1/1000/video-split-in`，回车即可。

另外，设置里的 `allowedRoots` 如果写了容器里并不存在的路径（默认是 `/vol1`～`/vol4`，
而机器上通常只有 `/vol1`），它们不会再出现在根目录下拉框里，而是单独提示一句「有几个根目录不存在」。

**某个视频切分失败？**
看该任务的日志。常见原因是文件本身损坏、或者不支持的编码。
把 `mode` 切到 `bytes` 通常能绕过——bytes 不解析视频结构，只切字节流。

**想先试一下再正式跑？**
设置里有 `debug` 开关，打开后只打印将要做什么、不实际动手。

**端口 8099 被占用？**
改 `.env` 的 `VS_PORT`。

## 目录结构

```
app/                FastAPI 服务端
  api/              各模块路由（system / settings / watchpoints / schedules / jobs / undo / ws）
  services/         业务：events 事件总线、queue 队列、runner 执行器、
                    scanner 扫描与稳定检测、monitor 目录监控、scheduler 定时
  config.py         配置读写（原子写 + 深合并 + 非法值纠正）
  db.py             SQLite（WAL、任务与日志）
  models.py         Pydantic 模型（camelCase 出入参）
core/               切割引擎（从 cli/ 版本演进而来）
  splitter.py       单文件切分，带进度回调与取消
  undo.py           撤销：校验 + 还原
cli/                原始命令行版本（独立可用，不依赖服务端）
web/                Vue 3 + TypeScript + Vite 网页控制台
docker/             Dockerfile、entrypoint、多架构构建推送脚本
deploy/             NAS 部署用的 docker-compose 与 .env 模板
fnos/               飞牛 fpk 应用包骨架（manifest / cmd / wizard / config / app）
tools/              冒烟测试、图标生成
docs/api.md         前后端接口契约
```

## 技术选型说明

| 选择 | 原因 |
|------|------|
| FastAPI 而非 Flask | 需要 WebSocket 推实时进度与日志，FastAPI 原生支持 async WebSocket |
| SQLite 而非 PostgreSQL | NAS 上多一个数据库服务是负担；单机单进程场景 SQLite 完全够，WAL 模式读写不互斥 |
| JSON 存配置而非数据库 | 配置要能手改、能直接备份、升级时能自动补默认值 |
| 单并发 worker | 切分是磁盘 IO 密集任务，并发跑多个只会让 NAS 磁盘来回寻道、整体更慢 |
| 前端构建产物由后端托管 | 一个端口一个容器，用户不用再配 nginx，也不用理解反向代理 |
| watchdog + 轮询双保险 | inotify 在网络共享目录上不生效，必须有兜底 |
| 镜像内置 ffmpeg | 让用户自己装 ffmpeg 是部署失败的最大来源 |
| gosu 而非 USER 指令 | 需要在启动时把挂载目录 chown 成 PUID 之后才降权，USER 指令做不到 |
